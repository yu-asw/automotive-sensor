Part B/SAE J3016

Automation levels 0–5 — the real border runs between L2 and L3

Per SAE J3016. What separates the levels is not capability but who watches the driving environment.

So where does our car sit? One indoor track, one lighting condition. The operating conditions are so narrow that a level number would mean nothing. What we build is a scale reproduction of L1–L2 features (LKA, AEB) — not a self-driving car.
Automotive Sensor · Lecture 1 · Part B12 / 42

Step height is degree of automation; the vertical dashed line is the liability border. Part B/Conclusion

That is why we use several sensors

Overlapping sensors of different character beats making one sensor better.

Camera

What is it

Lane markings, signal colour, sign text, pedestrian or cyclist — it reads meaning.

Weak at: night, backlight, fog; range is guesswork

Radar

How far and how fast

Range and relative speed in one shot, and almost untouched by rain, fog or darkness.

Weak at: shape. It has no idea what it hit

Lidar

Where, to the centimetre

3D shape and range to centimetre accuracy — the reference for mapping and precise localization.

Weak at: bad weather. And it is expensive

Filling in each other's blanks is sensor fusion. And performance is not the only reason to overlap — when one sensor returns a confidently wrong answer, catching it takes a sensor built on different physics. That is redundancy.

We only survey fusion, in Lecture 13. The real fusion theory belongs to Autonomous Driving (4-2). Our goal is the step before it — pulling in six kinds of data accurately and at the same time.

Part C/Definition

An embedded system does one fixed job, by a fixed deadline

How is it different from your laptop? Not in performance — in what is assumed.

General-purpose PCEmbedded system
PurposeAnything — the user decidesOne fixed job — the designer decides
TimeAverage throughput. Faster is betterA deadline. A late right answer is a wrong answer
ResourcesPlentiful. Add more if you run shortPower, memory, heat and cost are all fixed
EnvironmentIndoors, room temperature, clean powerFreezing, baking, vibration, sagging supply
When it failsYou rebootSomeone can get hurt
ExamplesLaptops, serversAirbag ECU, ABS, camera module, our D3-G
Real-time does not mean fast. It means a guarantee that the work finishes by a stated time. A system that always finishes within 10 ms beats one that averages 1 ms but occasionally takes 200 ms. In a car what counts is not the average but the worst case.
Automotive Sensor · Lecture 1 · Part C19 / 42

Break the "real-time = fast" misconception here. Use the airbag: from crash detection to deployment it must finish within tens of milliseconds, and being occasionally faster helps nobody. The "when it fails" row sets the character of automotive software as a whole.

Ask: your laptop freezing for three seconds is survivable. Why is it not survivable in a car?

Part C/CAN

ECUs talk to each other over one pair of wires: CAN

There are no addresses. Everyone hears everyone, and each node keeps only what it needs.

Classical CAN tops out at 1 Mbit/s with 8 bytes of payload. Camera video does not fit on that — which is why automotive Ethernet exists. The D3-G provides 3 CAN channels (transceivers live on a separate add-on board). We will not use them directly, but know CAN as the baseline of vehicle communication.
Automotive Sensor · Lecture 1 · Part C22 / 42

Three things about CAN — two differential wires, addressless broadcast, and ID = priority. The last one matters most: the moment a designer assigns a message ID, that message's real-time priority is fixed. Point out why the 8-byte limit matters and it leads straight into automotive Ethernet. This overlaps Automotive Networks (3-2), so do not go deep.

Ask: what fits in 8 bytes? (Four wheel speeds at 2 bytes each — exactly 8.)

Part C/Heterogeneous cores

Why mix cores of different character on one chip

Linux is comfortable, but it will not promise you a finish time. And some jobs in a car need that promise.

Application cores — Cortex-A72 / A53

Linux runs here

  • Filesystem, networking, drivers and libraries are all there already
  • OpenCV, GStreamer and ROS2 run as-is
  • But the scheduler makes no promise about when your code runs — sometimes it slips by tens of ms

Good fit: image processing · path decisions · logging · comms

Real-time core — Cortex-R5

An RTOS (FreeRTOS) runs here

  • The OS is small and simple, so response time is predictable
  • An interrupt is always serviced within a bounded time
  • But none of Linux's comforts — files and packages are on you

Good fit: vehicle comms · periodic control · safety monitoring

This is not a choose-one problem. The old way was a Linux board and an MCU sitting side by side, joined by wires. An automotive SoC puts both on one die and joins them with internal messages (IPC). Part count, wiring and latency all drop together.
Automotive Sensor · Lecture 1 · Part C25 / 42

The last line of the left card is the crux — on Linux, "usually 1 ms" is not "always 1 ms". Page faults, interrupts and other processes push it out now and then. A video frame arriving 20 ms late is survivable; motor PWM arriving 20 ms late makes the car lurch. That is why two kinds of core share one chip. We will not program the R5 ourselves, but they should know why the architecture looks like this.

Part C/Why this board

Why learn on an automotive SoC

There is an easier road. Four reasons we take this one instead.

  • You learn the structure. Heterogeneous cores, CAN, the boot chain — none of it exists on a Raspberry Pi. Most of what makes automotive software hard comes out of that structure.
  • The industry is heading this way. The "central compute" box in a zonal architecture is filled by this class of chip. Think back to the third panel on the previous slide.
  • You will actually meet this chip here. Telechips is a Korean automotive semiconductor company and TOPST is its official development platform. Work in automotive software in Korea and you will handle this family.
  • It carries past the semester. The same platform runs into the SEA:ME hackathon, capstone design, Automotive Vision (4-1) and Autonomous Driving (4-2). Your GitHub repo stays with you.
One thing to brace for — you will hit problems that a search engine cannot answer. On a Raspberry Pi, someone has already been there. On this board, maybe not. Reading the official docs, reading the logs, and asking — that is what the job actually is.
Automotive Sensor · Lecture 1 · Part C27 / 42

Read the four points plainly. The closing callout is the attitude of this course — getting stuck is normal, and the record of being stuck is the most valuable thing in the lab notebook. Remind them that with only two students, questions get answered on the messenger during the week too.

Part D/Linux

Why Linux

Not a matter of taste. Without these four, the car does not roll inside one semester.

  • The drivers already exist. Camera over V4L2, lidar over USB serial, sensors over I2C and SPI — the kernel already exposes all of it through standard interfaces. We just open /dev/video0.
  • The tools and packages exist. One line of apt brings in Python, OpenCV and GStreamer. Building that yourself would eat the whole semester.
  • ROS2 lives on Linux. The reference environment for ROS2 Humble is Ubuntu 22.04. That is the whole reason we use 22.04.
  • You can get in remotely. SSH in, read the logs, move files back and forth. You fix a board that is on the car from your desk.
The price is just as clear — Linux will not promise you a finish time. Exactly as in Part C. That is why an automotive SoC parks a real-time core next to Linux. So far it is the only way to get convenience and guarantees at once.

The screen you will stare at longest this term is the terminal. cd ls apt ssh vim, file permissions — that much should be in your fingers.

Automotive Sensor · Lecture 1 · Part D31 / 42

Isolation

One dies, the rest live

Each node is its own process. The lidar driver can crash and the camera keeps driving the car. And you can see immediately whose code broke.

Division of work

Two people never touch the same file

A publishes /camera/image_raw, B publishes /scan. All you agreed on was the topic name and the message type.

Tooling

See it, record it, replay it

rviz2 shows the lidar point cloud with your own eyes; rosbag records a whole run so you can replay it at your desk.

rosbag matters more than usual in this course. Sensor problems mostly appear only in that one moment. Record the run and you can replay the failure as many times as it takes. A failure you did not record cannot be analysed — and this is also where lab notebook evidence comes from.

The goal here is not to make you a ROS2 expert. If node, topic, publish and subscribe are enough to get sensor data flowing, that is enough.

What one lab-notebook entry contains

1 TheoryThree to five lines on this week. Name what you did not understand
2 ProgressDone / stuck on / what you tried / plan for next week
3 EvidenceMeasurements, plots, screenshots, scope captures, failure logs
4 Source codeCommitted to the same repository

Graded on specificity, not on length. Not "it didn't work" but "I fed it 3.3 V, the echo pin stayed dead, so I tried 5 V".

In a job interview, a graduate application or a hackathon, what proves "I built this" is not a transcript — it is this repository. And commit dates cannot be manufactured afterwards: fifteen weeks of weekly commits are their own evidence.
